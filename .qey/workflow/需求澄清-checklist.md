# 需求澄清 Checklist(Stage 0 过一遍 + 全程持续 sharpening)

> 写 spec 前先过这张清单,把边界问清。不涉及的标 —。

## 通用维度

- [ ] **业务域定位**:改哪个域?入口/调用方(codegraph_callers)
- [ ] **状态/流程**:涉及状态机?状态变更走唯一入口?
- [ ] **外部系统**:推/拉外部?同步还是异步(队列)?
- [ ] **金额/事务**:涉及金额?必须事务?
- [ ] **边界/异常**:正常路径 + 边界(空/超大/并发/重复) + 异常处理
- [ ] **验收标准(AC)**:怎么算做完了?可逐条核对的(写进 spec)

## 工程可靠性维度(改造类/涉及外部必过;简单需求标 —)

> 这类维度不过,上线必出事。决定 spec 的「可选节」要不要填。

- [ ] **跨系统交互**:涉及跨系统?接口契约(请求/响应/回调地址)?同步/异步?
- [ ] **幂等**:重复回调/重复请求如何处理?幂等键(单号/hash)?
- [ ] **回调可靠性**:外部回调可能丢失/延迟?重试策略?定时兜底扫描?
- [ ] **灰度/降级/回滚**:上线灰度?降级开关?回滚路径?异常切回旧逻辑?
- [ ] **对账/一致性**:本地 vs 外部状态如何校验?不一致如何处理?
- [ ] **数据迁移**(改造类):老字段/数据如何映射?入库顺序?老新并存?

## 持续 sharpening(不只是 Stage 0)

> 需求澄清不是过一遍就完,是**贯穿全程的持续行为**。

### 每次写 spec/design/tasks 时,主动检查:

- **术语冲突 challenge**:用户用的词和 `CONTEXT.md` 术语表冲突?→ **当场问**"你说的'订单'是 Order 还是 OrderLog?"
- **模糊术语 sharpen**:用户用了模糊/过载的词?→ **提出精确定义**并写入 CONTEXT.md
- **边界场景 stress**:讨论域关系时?→ **编造边界场景**逼用户精确(如"部分退款时,'已退款'是什么状态?")
- **代码对照**:用户说"系统这么跑"?→ **查代码验证**,矛盾时指出("代码 cancel 整个 Order,但你说支持部分取消——哪个对?")
- **ADR 三门槛**:出现决策?→ 满足 难逆/反直觉/真实取舍 才写 `knowledge/业务演进/`,否则跳过

> 这些不是额外步骤,是写 spec 时**同时发生**的——术语在讨论中**当场写进 CONTEXT.md**,不拖到收尾。
