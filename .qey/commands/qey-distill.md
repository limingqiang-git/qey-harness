# 知识提炼(刻意沉淀)

> **2.0 简化**:7 类触发 → **4 类**;校验(specs↔代码/domain 引用)抽到 `qey verify`(独立命令,不依赖触发判定)。
> **核心默认**:假设**没有可提炼的**。大部分任务做完,知识层不需要任何更新。

## 与 verify 的分工(2.0 新)

| 命令 | 干啥 | 何时跑 |
|------|------|--------|
| `qey verify` | 检测知识过期(只读,不改) | 改代码后 / commit 时自动 |
| `/qey:distill` | 提炼新知识(写入) | 周期/觉得该沉淀时 |
| `/qey:log` | 机械日志 | 会话结束 |

> **先 verify 后 distill**:verify 告诉你什么过期了,distill 决定加什么新的。

## Step 1:4 类触发判定

对本次 journal + 改动 + archive change,逐类问:

| # | 触发 | 问自己 | 命中 → 候选落点 |
|---|------|--------|--------------|
| 1 | **实现了功能 / 建立了约定** | 有新的行为契约(签名/参数/边界)或团队约定需要后人知道? | `specs/<域>/spec.md` 或 `rules/<层>/` |
| 2 | **做了设计决策 / 发现了模式** | 有"选 X 不选 Y,因为..."的取舍(ADR 三门槛)?或更好的代码结构该成规范? | `knowledge/业务演进/` 或 `rules/<层>/` |
| 3 | **修了 bug / 踩了 gotcha** | 坑**可复用**?有非显然的陷阱? | `knowledge/踩坑记录/` 或 `domain/业务术语.md` |
| 4 | **思维触发** | "做 X 前该先想 Y"(改状态机前先确认用哪个枚举)? | `rules/thinking-guides/` |

**判定结果**:
- **0 类命中** → "✓ 无可提炼"。**结束,不写任何东西。**
- **1+ 类命中** → 进 Step 2

## Step 2:落点候选(带范围检查 gate)

对每个命中项,生成 2-4 个候选落点。**每条必须带"范围检查"**——读目标文件的自述范围,对照本次内容,命中才推荐。

```
✓ [high] domain/业务领域/售后/物流拦截.md        (新文件)
   范围检查:✓ domain 定义"代码结构/入口/流程",在范围内
✗ [low] rules/历史遗留陷阱.md                    (不推荐)
   范围检查:✗ 该文件声明"命名/结构陷阱",本次是业务语义
```

## Step 3:Ask 二次确认(你拍板)

把候选清单摆给你,AskUserQuestion:勾选 / 改路径 / 新建 / 自定义 / 丢弃。**只有你确认的才落盘。**

## Step 4:用对应模板写入(确认后落盘)

每类触发对应一种写入模板。**所有知识必须带验证锚点 + last_verified + 置信度**。
> 📖 **填写参考**:写入前**先读目标目录的 `_example.md`**——参考填好的真实样本的质量和深度。

```markdown
### [YYYY-MM-DD] <标题> [observed|⚠️待确认|❓待确认]
- **锚点**:`Class::method` (app/path/file.php)  ← verify 用它检测过期
- **last_verified**: YYYY-MM-DD
- **内容**:...
```

> **锚点规范**(优先级):① 符号 `Class::method`(最稳)② 路径 `app/xxx.php`(次稳)③ 行号 `:56 (YYYY-MM codegraph)`(最弱,必须带日期)

## 引用规范(写知识时遵守)

| 类型 | 推荐写法 | 理由 |
|------|---------|------|
| **符号**(优先) | `OrderLogic::createOrder` | verify 能 grep 验证存在 |
| **路径**(次选) | `app/Order/Logics/OrderLogic.php` | verify 能测存在 |
| **行号**(辅助) | `:56 (2026-06 codegraph)` | 必须带日期(行号最易漂移) |

## 边界判定(该写哪个目录)

```
我要记的知识,核心是哪个问题?
├─ 现在代码的结构/入口/流程/状态?     → domain/
├─ 代码应遵守的行为契约/不变量?       → specs/
├─ 为什么这么设计/选 X 不选 Y?        → knowledge/业务演进/(ADR)
├─ 踩过的、别人会再踩的坑?           → knowledge/踩坑记录/
├─ 今后所有人写代码必须遵守的约束?     → rules/
└─ 都不沾 → 不写(默认无可提炼)
```
