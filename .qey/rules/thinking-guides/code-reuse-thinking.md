# Code Reuse Thinking Guide(复用思维)

> 写新代码前先搜。重复代码是不一致 bug 的 #1 来源。
> 改常量/配置前先搜所有引用。新建工具函数前先搜有没有。

## 触发条件(命中就读本 guide)
- 你在写和已有代码相似的逻辑
- 同一模式重复 3+ 次
- **你在改任何常量或配置** ← 先搜!
- **你在新建工具函数** ← 先搜!
- 两个文件各自解析同一个 untyped 字段

## 该问自己的问题

### 1. 类似的函数/逻辑已经存在吗?

```bash
# 先搜!别急着写
grep -r "functionName" .
grep -r "keyword" .
```

| 问题 | 如果 Yes... |
|------|------------|
| 有类似函数吗? | 用它或扩展它 |
| 这个模式别处用过吗? | 遵循现有模式 |
| 这能是共享工具吗? | 放到正确的共享位置 |
| 我在从别的文件复制代码? | **停!** 提取到共享 |

### 2. 我在改常量/配置/枚举值吗?

```bash
# 改任何值前,搜所有引用!
grep -r "value_to_change" .
```

> ⚠️ "改了一个常量,忘了更新别处"是 #1 的"forgot to update X" bug。
> 这个习惯能防住大部分此类 bug。

### 3. 同一个 untyped payload 字段被多处解析吗?

**症状**:多个消费者各自 cast 同一个 JSON/Event 字段:
```php
// 消费者 A
$desc = $event['description'] ?? '';
// 消费者 B
$desc = (string)($ev['description'] ?? '');
```

**问题**:每个消费者有自己的"什么是合法 payload"的定义。payload 结构变了,有的消费者更新有的没 → 不一致。

**修正**:把 decoder/type guard 放在数据所有者旁边,所有消费者调它。

**规则**:同一 untyped 字段被读 2+ 处 → 提取共享 decoder,别加第三个。

## 什么时候抽象(别过度)

**该抽象**:
- 同样代码出现 3+ 次
- 逻辑复杂到可能有 bug
- 多人可能需要

**别抽象**:
- 只用一次
- 简单的一行
- 抽象比重复更复杂

## 常见重复模式

### 模式 1:复制粘贴函数
- **反例**:把校验函数复制到另一个文件
- **正例**:提取到共享工具,import

### 模式 2:重复定义常量
- **反例**:多个文件各自 define 同一个常量
- **正例**:单一真相源(项目的 `Constants/` 目录),到处 import

### 模式 3:分散的状态判断
- **反例**:`if ($status === 'opened') {...} elseif ($status === 'paid') {...}` 散落多处
- **正例**:一个 reducer/state machine 拥有完整流转表

## 批量改动后的检查

当你对多个文件做了相似改动:
1. **复查**:全找到了吗?
2. **搜索**:`grep` 找漏的
3. **考虑**:该抽象吗?

## 指向

- 项目特定重复陷阱 → `rules/历史遗留陷阱.md`(如"两套 Service""Repository 按存储分目录")
- 代码规范 → `rules/shared/` 或 `rules/backend/`
