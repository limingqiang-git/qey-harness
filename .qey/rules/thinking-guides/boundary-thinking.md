# Boundary Thinking Guide(边界思维)

> 动手前先认清:这个业务/数据/操作,**本系统管还是上游系统管**?
> 订单中心**不是**所有业务的主系统。在错误的地方找逻辑 = 白费时间。

## 触发条件(命中就读本 guide)
- 你在找售后/退款/库存的逻辑(⚠️ 可能不在本系统!)
- 你不确定某操作该在订单中心还是上游系统
- 你在写对外 RPC(边界在哪)
- 你在处理跨系统数据一致性

## 该问自己的问题

### 1. 这个实体/操作,本系统是"主"还是"只读/只执行"?

> 来自项目 `knowledge/项目级记忆.md` 的"架构边界"段(⭐ 重要):

| 实体 | 谁是主系统? | 订单中心的角色 |
|------|------------|--------------|
| **售后单 `after_sale`** | 上游系统创建维护 | **只读查询**(`getOrderAfterSaleList`)+ 发状态事件。**不创建、不审批** |
| **退款单 `refund_order`** | 上游创建 | **只执行退款**(唯一写:`updateProcessingStatus` PENDING→PROCESSING) |
| **库存** | 在 OMS | **只通知**(`RingStockInventoryConsumer`→OMS RPC),**不操作库存表** |
| **售后审批** | 在上游 | `ApprovalService::canAudit` 仅用于圈备货释放单**展示** |

**动手前问**:我要找的逻辑,确定在订单中心吗?
- 不确定 → 先查 `domain/业务流程.md` 的"架构边界"段
- 在上游 → 别在订单中心找,去对应系统

### 2. 这个操作该谁发起?

| 场景 | 该谁做 |
|------|--------|
| 创建售后单 | ❌ 订单中心不做(上游做) |
| 审批售后 | ❌ 订单中心不做(上游做) |
| 执行退款 | ✅ 订单中心做(但退款单是上游创建的) |
| 扣库存 | ❌ 订单中心不做(OMS 做;订单中心只通知) |
| 查售后列表 | ✅ 订单中心做(只读) |

### 3. 跨系统数据一致性问题

> 来自项目 `knowledge/项目级记忆.md` 的"系统性风险"段:多处"通知/异步"是 best-effort,**失败即丢、无补偿**。

你在写跨系统通知/异步时:
- [ ] 失败了会丢吗?(`requeue:false` + NACK = 丢)
- [ ] 有补偿/对账机制吗?
- [ ] 本地落库了吗?(失败可查可补)
- [ ] RPC 在事务内还是外?(事务外 RPC 成功 + 本地 save 失败 = 渠道有单本地无记录)

> ⚠️ `XyPayService::createPay` 的 RPC 在 `orderPayRepo->save` 事务**外** → 这个模式的风险要知道。

### 4. 多租户边界

> 来自项目陷阱:协程内必须 `TenantManager` 切 DB connection。

你在写跨租户操作时:
- [ ] 当前在哪个租户的 connection?
- [ ] 跨协程透传了吗?(`Kernel/Context/Coroutine`)
- [ ] 会不会误操作别的租户的数据?

## 常见边界错误

### 错误 1:在订单中心找售后审批逻辑
- **症状**:grep 不到审批实现
- **原因**:审批在上游系统,订单中心只有 `canAudit`(展示用)
- **修正**:去上游系统找

### 错误 2:直接操作库存表
- **症状**:在订单中心写库存 CRUD
- **原因**:库存主数据在 OMS
- **修正**:订单中心只通过 RPC 通知 OMS,不碰库存表

### 错误 3:跨系统调用不放事务里/外想清楚
- **症状**:RPC 成功但本地落库失败(或反之),数据不一致
- **修正**:明确 RPC 和本地事务的边界(通常:本地事务先,事务外发 RPC/事件)
